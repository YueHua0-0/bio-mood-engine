## 1. 背景与目标
睡眠中的角色不该被普通群消息叫醒，但冲突与管理员指令必须立刻到达。本模块把"这条消息现在要不要出现、要不要叫醒、还是留到醒来"变成确定性判定：先算事件紧急度，再算唤醒代价，按五条规则命中即停给出 `delivery.policy`，并给出可执行的排队时间与过期时间。

本模块输出的是**策略**，不是动作：引擎不发送消息、不调用 DSH、不写队列存储；发送与唤醒由宿主和 DSH 依据策略执行。全部判定参数均为**虚构角色状态模拟**，不是人体医学模型，不用于诊断、治疗或现实健康预测；`sleep_debt` / `sleepiness` 是模拟量。

### 1.1 关键约束（摘自 00，不得改动）
- `delivery.policy` 只能取 00 §2.7 的五个枚举值，不得新增。
- 判定必须按 §5.3 的固定优先级执行，命中即停，不得并行打分取最大。
- `reason_codes` ≤16 个、稳定命名（`^[a-z][a-z0-9_]{0,63}$`），排序固定。
- 纯函数：不读系统时间、不访问网络/存储、不发送消息、不使用 `Math.random()`；本模块不消费随机数。
- `silent_ignore` 是"不触发 DSH 但保留记录"，**不得**被实现成丢弃或静默跳过。

## 2. 范围与非目标
**范围**：紧急度基表与 @ 修正；唤醒代价；五条策略规则；排队延迟与上限；同会话 10 分钟合并；交付前重新校验；`silent_ignore` 与 `queue_until_awake` 的语义区分；原因码与精度。

**非目标**：不发送消息、不调度定时器、不写任何存储（13 负责）；不判断消息内容重要性（适配层给 `relationship_tag` 与 `event_type`）；不计算睡眠与压力（06/07）；不生成行为倾向（10）；不做重试与限流（12/13）。

| `recommended_delay_seconds` | integer | 仅 `queue_until_awake` 非 0，其余为 `0` |
| `deliver_after` | string | `now` 或 `now + delay`，UTC 毫秒 `Z` |
| `expires_at` | string \| null | 仅 `queue_until_awake` 为 `deliver_after + 24h`，其余 `null` |
| `reason_codes` | string[] | ≤16 个，顺序见 §5.8 |
| `coalesced_into` | object \| 省略 | 见 §5.5；仅同会话合并触发时出现，其余**整键省略**（不输出 `null`），内部字段见 00 §12.4 |

## 5. 算法与规则

### 5.1 紧急度基表（冻结）
| `event_type` | `urgency` | `event_type` | `urgency` |
| --- | --- | --- | --- |
| `conflict` | 1.00 | `mention` | 0.60 |
| `admin_command` | 0.90 | `comfort_received` | 0.50 |
| `important_person_appear` | 0.75 | `group_message` | 0.20 |
| `direct_question` | 0.70 | `long_silence` | 0.10 |
| `system_event` | 0.00 | — | — |

`is_mentioned === true` 时：`urgency = max(base, 0.60)`，其余情况直接取基表值。该修正只上调、不下调（`base ≥ 0.60` 时保持原值）；`system_event` 被 @ 时按 `max(0, 0.60) = 0.60` 处理，不得特殊化。

### 5.2 唤醒代价
```text
wake_cost = clamp(0.30 + 0.45*sleep_debt + 0.30*sleepiness - 0.20*urgency, 0, 1)
```
输入先 `clamp(0,1)` 再代入。语义：睡眠债越高、越困、事件越不紧急，叫醒代价越大。`wake_cost` 必须在策略判定**之前**算好并被输出，供宿主解释。

### 5.3 策略判定（严格按优先级，命中即停）
```text
00  if event === null:                                       policy = silent_ignore; reason_codes = ['no_event']
01  if sleeping and urgency >= 0.95 and wake_cost <= 0.85:  policy = urgent_interrupt
02  elif sleeping and urgency >= 0.70 and wake_cost < 0.70: policy = wake_candidate
03  elif sleeping:                                           policy = queue_until_awake
04  elif awake and sleepiness >= 0.85 and urgency < 0.50:    policy = silent_ignore
05  else:                                                    policy = deliver_now
```

- 规则 0 优先于一切：只在 `inputs.event === null` 时命中，命中即停，不参与策略判定、不算 `urgency`、不进入规则 1–5；`reason_codes` 只有 `no_event` 一个（v1.7.9）。**但为生成诊断性 `wake_cost`（§4.2 要求 `event=null` 仍输出该字段），规则 0 允许读取 `sleep_debt` / `sleepiness` 并按 §5.6 的缺失值降级处理**（P-11-02，裁决 A）——这里的"不读 sleep"仅指不把睡眠状态用于规则 1–4 的分支判定。
- 规则 1–3 只对 `sleep.state === 'sleeping'` 生效；规则 4 只对 `awake` 生效。
- `sleepy` / `trying_to_sleep` / `interrupted` / `waking_up` 不进入 1–4，直接落到规则 5 `deliver_now`，并追加 `sleepy_passthrough`；若产品需要把这些状态也纳入延迟，属契约变更，不得在实现中私改。
- 边界一律用闭/开区间严格比较，`1e-9` 容差；`urgency` 先 `round6` 再比较，避免 `0.9499999` 误判。

### 5.4 排队计算（`queue_until_awake`）
| 项 | 规则 |
| --- | --- |
| `recommended_delay_seconds` | `max(0, floor((planned_wake_at - now) / 1000))`，缺失 `planned_wake_at` 时取 `1800` |
| 上限 | `min(delay, 86400)`；被截断追加 `queue_capped` |
| `deliver_after` | `now + recommended_delay_seconds` |
| `expires_at` | `deliver_after + 86400 秒`（24 小时） |
| 缺失计划唤醒 | 追加 `planned_wake_missing`，不得报错 |

延迟计算使用整数秒向下取整（宁可早一点醒，不因舍入晚交付）；`planned_wake_at` 已过时 `delay = 0`，仍走 `queue_until_awake` 并在下一次重新校验时自然转为 `deliver_now`。

**缺失 `planned_wake_at` 的语义**：`1800` 是**重新校验间隔**，不是交付时刻。宿主在 `deliver_after` 时调用 `recheck`：仍为 `sleeping` 且未过期 → 顺延 `1800` 秒并保留 `queue_until_awake`；转为 `awake` → `deliver_now`；超过 `expires_at` → `silent_ignore`。不得在仍睡眠时直接交付。

**无消息级订阅时的约束（01 A9）**：若阶段 0 结论为"插件无法在消息到达时被调用"，`deliver_after` 只是"最早可交付时刻"，宿主不保证准点；必须在下次 `observe` / 管理员 `tick` 推进时重估——已过 `deliver_after` 且未过期则 `deliver_now`，仍在睡眠则继续 `queue_until_awake`，已过 `expires_at` 则 `silent_ignore`。不得依赖定时器，也不得声称"准点送达"。

### 5.5 冷却与合并
| 触发条件 | 处理 | 输出 |
| --- | --- | --- |
| 同一 `conversation_id` 在 `(now-600s, now]` 内累计 `queue_until_awake` 项（含本条）≥3，且本条策略为 `queue_until_awake` | 合并为 1 条：保留最早 `queued_at`（相同则取 `event_id` 字典序最小者），其余项不再单独交付 | 本条返回 `silent_ignore` + `reason_codes` 追加 `coalesced` + `coalesced_into` |
| 累计 <3，或本条策略不是 `queue_until_awake` | 按原策略输出 | `queue_until_awake` 等 |

```text
coalesced_into = {
  event_id: 保留项.event_id,
  conversation_id,
  earliest_queued_at: 保留项.queued_at,
  merged_count: 窗口内同会话 pending 条数 + 1        // 含本条
}
```

- `merged_count` 通过 `coalesced_into` 返回（00 v1.7.8 §12.4），不得塞进 `reason_codes`，也不得写进 `warnings`。
- **11 不计算 `urgency`**：`inputs.queue.pending` 只含 `{conversation_id, queued_at, event_id}`，11 无从得知各条紧急度；合并项均为 `queue_until_awake`（`urgency < 0.70`），对交付策略无区分意义。"窗口内最大 `urgency`"由 13 按其队列记录维护（13 是队列所有者）。
- 合并产生的 `silent_ignore` 的其余字段按 §4.3 填：`wake_candidate=false`、`recommended_delay_seconds=0`、`deliver_after=now`、`expires_at=null`；`wake_cost` 仍须在判定前算好并输出。
- 若合并后策略不是 `silent_ignore`，视为实现错误 → `MODULE_FAILED`（§6）。

合并后的唯一记录仍需在醒来后交付一次；被合并项**不得**丢弃，只在交付计划中折叠。`silent_ignore`（含合并产生的）必须写事件日志（字段见 00 §10.1），只省掉 DSH 触发。

### 5.6 交付前重新校验
| 重新校验结果 | 处理 | 附加原因码 |
| --- | --- | --- |
| `sleep.state` 已变为 `awake` | 改判 `deliver_now`，`delay = 0` | `state_changed_awake` |
| `expires_at` 已过（`now > expires_at`） | 改判 `silent_ignore`，且不再交付 | `expired` |
| 仍为 `sleeping` 且未过期 | 保持原策略；若 `planned_wake_at` 缺失，`delay += 1800` 后再次校验 | — |
| 状态与项不属于同一 `character_id` | 拒绝 | `INVALID_REQUEST` |

重新校验发生在"打算交付的那一刻"，由宿主调用；引擎只提供纯函数 `recheck`，不自行计时。

### 5.7 静默忽略与延迟交付的区别
| 维度 | `silent_ignore` | `queue_until_awake` |
| --- | --- | --- |
| 是否触发 DSH | 否 | 现在不触发，醒来后触发 |
| 是否保留记录 | 是（事件日志） | 是（事件日志 + 交付计划） |
| 醒来后是否交付 | 否 | 是，且仅交付一次 |
| 典型原因 | 高困倦低优先、合并折叠、已过期 | 睡眠中非紧急事件 |

### 5.8 原因码（≤16，顺序固定）
| 顺序 | 码 | 触发条件 |
| --- | --- | --- |
| 1 | `no_event` | `inputs.event === null`（纯时间推进，规则 0；v1.7.9） |
| 2 | `sleeping` | `sleep.state === 'sleeping'` |
| 3 | `urgent_conflict` | 命中规则 1 |
| 4 | `wake_candidate_low_cost` | 命中规则 2 |
| 5 | `wake_cost_high` | `sleeping` 且 `wake_cost` 使规则 1 或 2 未能命中 |
| 6 | `low_event_urgency` | `sleeping` 且 `urgency < 0.70` |
| 7 | `awake_high_sleepiness` | 命中规则 4 |
| 8 | `sleepy_passthrough` | 非 `sleeping` / `awake` 状态直接放行 |
| 9 | `planned_wake_reached` | 延迟计算使用了有效 `planned_wake_at` |
| 10 | `planned_wake_missing` | 使用默认 `1800` 秒作为重校验间隔 |
| 11 | `queue_capped` | 延迟被 `86400` 截断 |
| 12 | `coalesced` | 10 分钟窗口内同会话合并 |
| 13 | `state_changed_awake` | 重新校验时已醒 |
| 14 | `expired` | 重新校验时已过期 |

排序按本表自上而下，去重后最多 14 个；实现不得发明新码而不登记。`no_event` 与其余所有码**互斥**：出现时不得再追加 `sleeping` / `coalesced` / `low_event_urgency` 等（规则 0 命中即停）。

### 5.9 精度与确定性
`wake_cost` 与所有比较量先 `round6`；`recommended_delay_seconds` 为整数秒；`deliver_after` / `expires_at` 为 UTC 毫秒 `Z`。同 `inputs` + 同 `previous` + 同 `now` 必得深度相等结果；不写存储、不改入参、不产生副作用。

## 6. 边界与错误
| 场景 | 处理 | 错误码 / 警告 |
| --- | --- | --- |
| `event_type` 非枚举 | 拒绝，不兜底成 `group_message` | `INVALID_REQUEST` |
| `sleep.state` 非枚举 | 按 `awake` 处理 | `DEGRADED` + `UNKNOWN_SLEEP_STATE` |
| `sleepiness` / `sleep_debt` 缺失 | 取 `0.25` / `0.15` | `DEGRADED` + `MISSING_SLEEP_DATA` |
| 数值越界 | 钳制 `[0,1]` | `INPUT_CLAMPED` |
| 数值 `NaN` / `Infinity` | 拒绝本次判定 | `INVALID_REQUEST` |
| `planned_wake_at` 格式非法 | 视为缺失，用 `1800` | `planned_wake_missing` |
| `planned_wake_at` 已过 | `delay = 0`，下次重新校验转 `deliver_now` | 成功 |
| `now` 非 UTC 毫秒 | 拒绝 | `INVALID_TIME` |
| `pending` 缺 `conversation_id` | 不参与合并 | `DEGRADED` |
| 合并后策略非 `silent_ignore` | 视为实现错误 | `MODULE_FAILED` |

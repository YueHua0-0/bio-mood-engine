## 1. 背景与目标

所有模块都依赖三件事：**状态的形状**、**时间的解释**、**推进的顺序**。这三件事一旦漂移，后续 12 个模块会产生无法定位的数值错误。本任务书要求把这三件事一次性做成可测试的公共能力：

- `models.mjs`：状态的构造、校验、范围裁剪、`round6`、快照摘要；
- `clock.mjs`：UTC 解析、本地时间分解、时钟回拨处理、离线分块；
- `coordinator.mjs`：固定流水线、模块注册与失败回滚；
- `versioning.mjs`：`schema_version` 迁移与 `engine_version` 兼容判定。

**本任务书不实现任何生理/情绪算法。** 周期、睡眠、压力、调节、情绪的计算分别属于 05–09；协调器只负责"按顺序调用它们"。

### 1.1 关键约束（摘自 00，不得改动）

- 状态数值统一 `[0,1]`；贡献值 `[-1,1]`；持久化前 `round6`。
- 时间统一 UTC ISO 8601 毫秒 + `Z`；本地时区单独保存为 IANA。
- 单步最大 1 小时；最多 4320 步；超出走 `coarse_forward`。
- 模块是纯函数，不读系统时间、不访问网络/存储。
- 一次推进必须在同一事务内完成，失败回滚，`state_version` 不变。

## 5. 算法与规则

### 5.1 默认状态工厂

首次初始化（无既有状态）时：

```text
schema_version = 1
engine_version = 传入版本
state_version  = 0
created_at = updated_at = last_tick_at = now
timezone = 配置时区（必须能被 Intl 接受，否则 INVALID_REQUEST）
config_version = 配置版本
cycle   = 由 05 提供初始值（本模块只校验形状；未接入时用契约默认）
sleep   = awake / sleep_debt 0.15 / sleep_quality 0.7 / sleepiness 0.25 / circadian_phase 由 now 计算
stress  = level 0.15 / active_events []
regulation = 六维取配置默认值（通常 0.5）
mood    = 七维取配置默认值
random  = 由 03 派生五个流，counter 全为 0
```

默认值必须集中在 `DEFAULT_STATE` 常量中，禁止散落在多个函数内。

### 5.2 `normalizeState` 规则

对每个数值字段：

```text
v = Number(v)
if (!Number.isFinite(v)) -> INVALID_REQUEST（不得默默改 0）
v = Math.min(max, Math.max(min, v))
v = round6(v)
if (Object.is(v, -0)) v = 0
```

`round6`：

```js
export function round6(v) {
  const r = Math.round(v * 1e6) / 1e6;
  return Object.is(r, -0) ? 0 : r;
}
```

数组字段：

- `stress.active_events`：过滤 `Math.abs(remaining) < 0.005`，按 `Math.abs(remaining)` 降序，截断到 32 条（负强度事件必须与正强度同权保留）；
- 任何重复 `event_id` 只保留 `Math.abs(remaining)` 较大的那条；
- `random.streams` 的键集合必须恰好是 `cycle|sleep|mood|event|delivery`，多一个少一个都报错。

### 5.3 时间钳制（实现 00 §5.2）

```text
lastTickMs = parseTime(state.last_tick_at, 'last_tick_at')
nowMs      = parseTime(now, 'now')
delta      = nowMs - lastTickMs

if delta < -300_000:                       // 回拨超过 5 分钟
    effective_now = state.last_tick_at
    warnings.push('CLOCK_REGRESSION')
else if delta < 0:                         // 5 分钟内回拨
    effective_now = state.last_tick_at
    warnings.push('CLOCK_TOLERATED')
else:
    effective_now = now
```

事件时间：

```text
if occurred_at > received_at + 300_000:
    occurred_at = received_at; warnings.push('FUTURE_OCCURRED_AT')
if occurred_at < lastTickMs - 180*86400*1000:
    warnings.push('EVENT_TOO_OLD')   // 仍记录事件，但不回放历史
```

**注意**：回拨时 `effective_now` 等于 `last_tick_at`，即 `elapsed = 0`，流水线仍要执行（用于消费事件），但不得改变任何由时间驱动的量。

**落地位置（P-02-02）**：`occurred_at` 超前钳制发生在 `POST /v1/events` 入口（`lib/api/handler.mjs` 的 `clampEventTime`），先于幂等判定与推进；`evlog` 与推进基准都用钳制后的时间。`effectiveNow()` 只保证推进基准不回退，不处理事件时间。恰好 `+300000 ms` 不钳制。

### 5.4 离线分块

```js
export function chunkElapsed({ elapsedSeconds, maxSteps = 4320, maxChunkSeconds = 3600 }) {
  const out = [];
  let remaining = Math.max(0, Math.floor(elapsedSeconds));
  let steps = 0;
  while (remaining > 0 && steps < maxSteps) {
    const take = Math.min(remaining, maxChunkSeconds);
    out.push(take);
    remaining -= take;
    steps += 1;
  }
  return { chunks: out, leftoverSeconds: remaining, coarse: remaining > 0 };
}
```

约束：

- 每个 chunk 的结束时间 `t_k = last_tick + Σ chunks[0..k] * 1000`；
- `chunks` 长度上限 4320，绝不 `while (elapsed > 0)` 无上限；
- 浮点秒必须先 `Math.floor`，避免 59.999 产生 2 步。

`coarseForward` 只在 `leftoverSeconds > 0` 时调用一次，规则：

| 量 | 粗推进规则 |
| --- | --- |
| `mood.*` | 向各维 `home` 线性收敛：`v = home + (v-home) * exp(-days/7)` |
| `stress.level` | `level *= exp(-days/2)`，并清空 `Math.abs(remaining) < 0.005` 的事件 |
| `sleep.sleep_debt` | 净变化公式：`sleep_debt += (0.014 × 16 − 0.075 × 0.7 × 8) × days`，再 `clamp(0,1)`。即按"每天 16 小时清醒 + 8 小时睡眠（质量 0.7）"的日均净变化 `−0.196/天`，不再分别加、减 |
| `cycle` | 按整天推进（见 05 的 `advanceCycleDays`），允许一次跨多周期 |
| `sleepiness` | 取本地时间对应昼夜目标的稳态值 |
| `sleep.state` | 若粗推进跨越 `planned_wake_at`，置 `awake`，`last_transition_reason='coarse_wake'` |

粗推进必须追加 `LONG_OFFLINE_COARSE` 警告并把跨度小时数作为后缀参数（格式 `LONG_OFFLINE_COARSE:<小时>h`，如 `LONG_OFFLINE_COARSE:720h`），与 00 §5.3"在 warnings 中记录实际跨度"一致；警告码本体仍为 `LONG_OFFLINE_COARSE`。

`cycle` 与 `sleepiness` 两行**必须**使用 05/06 注入的实现：`hooks.advanceCycleDays({ cycle, deltaDays, rngProvider, config })` 与 `hooks.sleepinessSteady(localHour, sleepDebt)`（协调器从模块对象的同名属性取，见 §5.5）。**`rngProvider` 必须原样透传**：离线跨度跨多个周期时，`advanceCycleDays` 要为每个新周期用 `cycle:${index}` 流各采样 1 次；缺失 provider 只能退化为 28.4 常数推进，会让 180 天粗推进与逐小时推进的 `cycle_length_days` 不一致（C12）。02 内**不保留**"滚动天数"或昼夜公式副本；缺失对应 hook 时抛 `MODULE_FAILED`（`details.module` 为 `cycle` / `sleep`），不得静默退化（I-3 / I-4）。

### 5.5 流水线

```js
export function advance({ state, event, now, rngProvider, config }) {
  const { effective_now, warnings: coordWarnings } = effectiveNow({ now, lastTickAt: state.last_tick_at });
  const { chunks, leftoverSeconds, coarse } = chunkElapsed({
    elapsedSeconds: diffSeconds(state.last_tick_at, effective_now)
  });

  let draft = structuredClone(state);
  let t = state.last_tick_at;
  let delivery = null;
  let behavior_context = null;
  // 各模块 ModuleResult 的暂存数组；返回前由 aggregateDiagnostics 汇总为 00 §11.4 的 diagnostics 对象
  const moduleResults = [];

  for (const step of chunks) {
    const stepEnd = parseTime(t) + step * 1000;
    let guard = 0;
    while (parseTime(t) < stepEnd && guard < 9) {
      guard += 1;
      const rngSnapshot = rngProvider.serialize();
      const prevDraft = draft;
      const prevDelivery = delivery;
      const prevBehavior = behavior_context;
      const resultMark = moduleResults.length;

      let res = runPipeline({ draft, event: null, now: toIso(stepEnd), rngProvider, config, moduleResults,
                              previousBehaviorContext: behavior_context });
      draft = res.state;
      delivery = res.delivery;
      behavior_context = res.behavior_context;
      let nextMs = stepEnd;

      // 00 §4.2 / §5.4.2：若提示的转换点落在本片内，丢弃本次结果，
      // 用同一随机快照重算到该时刻，保证转换精确发生且不重复消耗随机数。
      if (res.next_transition_at) {
        const hintMs = parseTime(res.next_transition_at, 'next_transition_at');
        if (hintMs > parseTime(t) && hintMs < stepEnd) {
          draft = prevDraft;
          delivery = prevDelivery;
          behavior_context = prevBehavior;
          moduleResults.length = resultMark;
          rngProvider = RandomProvider.restore(rngSnapshot);
          res = runPipeline({ draft, event: null, now: res.next_transition_at, rngProvider, config, moduleResults,
                              previousBehaviorContext: prevBehavior });
          draft = res.state;
          delivery = res.delivery;
          behavior_context = res.behavior_context;
          nextMs = hintMs;
        }
      }
      t = toIso(nextMs);
    }
  }
  if (coarse) {
    draft = coarseForward({ draft, leftoverSeconds, config, moduleResults });
    coordWarnings.push(`LONG_OFFLINE_COARSE:${Math.round(leftoverSeconds / 3600)}h`);
  }
  // 最后一轮才应用新事件，保证事件只被计入一次
  if (event) {
    const res = runPipeline({ draft, event, now: effective_now, rngProvider, config, moduleResults,
                              previousBehaviorContext: behavior_context });
    draft = res.state;
    delivery = res.delivery;
    behavior_context = res.behavior_context;
  }
  // 00 §11.4 方案 A：写回随机计数器；调用方不得再次自行持久化 provider
  draft.random = rngProvider.toPersisted();
  draft.state_version = state.state_version + 1;
  draft.updated_at = draft.last_tick_at = effective_now;
  const diagnostics = aggregateDiagnostics(moduleResults);
  diagnostics.warnings = [...coordWarnings, ...diagnostics.warnings];
  return { state: normalizeState(draft), delivery, behavior_context, diagnostics };
}
```

`aggregateDiagnostics(moduleResults)` 把暂存数组汇总为 00 §11.4 的 `diagnostics` 对象：`contributions` 同键累加、**`warnings` 按序拼接后按"已去重保留首次出现"处理（模块级与协调器级一视同仁）**、`module_ms` 以模块名为键累加耗时。`advance` 随后把协调器级警告前置合并进 `diagnostics.warnings`，合并结果再整体去重并截断到 16 条。去重是为了吸收 05 与 09 在周期降级时同时追加的 `MISSING_CYCLE_DATA`（00 §4.2 / 09 §5.6）。返回对象只有 `state` / `delivery` / `behavior_context` / `diagnostics` 四个键，协调器级警告（时钟回退、`LONG_OFFLINE_COARSE`）一律并入 `diagnostics.warnings`，**不存在顶层 `warnings` 字段**。

**不可变性约束（实现必须遵守）：** `runPipeline` 与每个模块都必须**返回新的 state 对象，不得原地修改入参 `draft`/`previous`**（00 §4.3 第 1 条）。`advance` 里的 `prevDraft = draft` 只保存引用——一旦下游原地修改，回滚与"丢弃重算"都会失效，`structuredClone` 的保护在第一次调用后即被破坏。因此协调器与 14 的形状测试都应校验：调用前后入参对象引用不变、内容不变（`Object.freeze` 深冻结桩可用于该断言）。

**关键规则：事件只在最后一个 chunk 应用。** 否则离线 3 天时同一条消息会被重复计入 72 次。这是 G1 的必测项。

**C-06-01 事件预判与回滚重跑：** 事件落地前，先调用 07 的 `applyEvent` 取 `derived.event_intensity`，再调用 11 的纯函数预判交付策略。预判为 `urgent_interrupt` 时，用 `serialize()` 快照回滚 `rng`，把 `urgent_interrupt: true` 与合法强度注入 06，再重跑整条流水线。**对外返回的 `delivery` 保留预判结果**，第二遍只更新 `state` 与 `behavior_context`，不得覆盖 `delivery`——否则 06 转为 `waking_up` 后 11 会重算成 `deliver_now`，15 的 E03 无法通过。预判只读、不提交，回滚重跑消耗的随机数与单遍路径一致。

**时间片细分规则：**

- 一次细分会先按片末计算，再按提示时刻重算；被丢弃那次产生的模块结果必须一并回滚（实现上记录 `moduleResults.length` 后截断）；
- 随机数必须用 `serialize()` 快照回滚，禁止"重算两次、消耗两倍随机数"；
- 每小时最多细分 8 次（`guard < 9`），防止模块持续给出抖动提示；
- 提示非法（早于当前时刻、晚于片末、格式错误）时忽略，并追加 `INVALID_TRANSITION_HINT`；
- 若同一片内多个模块都给出提示，取最早值；实现上由 `runPipeline` 汇总后返回单个 `next_transition_at`。

`runPipeline` 的固定顺序（与 00 §5.4 一致）：

```text
1 cycle      -> {cycle, contributions, derived.phase_impact}
2 sleep      -> {sleep, contributions}
3 stress     -> {stress, contributions}    // 先衰减旧事件
4 event      -> {stress, contributions}    // 再应用新事件（仅写 stress）
5 regulation -> {regulation, contributions}
6 mood       -> {mood, contributions}      // inputs.cycle.phase_vector = 第 1 步的 derived.phase_impact
7 behavior   -> {behavior_context}         // 只读 mood/regulation/sleep；previous_context = 入参 previousBehaviorContext
8 delivery   -> {delivery}                 // 只读 state + config，不写 state
```

**`previousBehaviorContext` 的传递规则**（10 §4.2 / §5.4–§5.5）：`advance` 维护 `behavior_context` 变量，每次 `runPipeline` 调用时把**上一 chunk 的结果**作为 `previousBehaviorContext` 传入，协调器再把它作为 10 的 `previous_context`；首次调用传 `null`，10 走无滞回判定并追加 `HYSTERESIS_RESET`。重算分支必须回退到 `prevBehavior` 再传，保证滞回输入与丢弃前一致。`behavior_context` **不持久化**（10 §2），因此跨 `advance`（跨工具调用、跨进程重启）一律 `HYSTERESIS_RESET`，只有同一次 `advance` 的多 chunk 间生效。

`runPipeline` 返回 `{state, delivery, behavior_context, next_transition_at}`；各模块的 `ModuleResult` 追加到入参 `moduleResults` 数组，最终由 `aggregateDiagnostics` 汇总为 00 §11.4 的 `diagnostics` 对象。7/8 由协调器内部调用，**API/适配层不得在 `advance` 之后重复调用**。

**`derived` 的传递规则**（00 §4.2）：`runPipeline` **每次调用都重新构造一个 `derived` 累加对象**（不跨调用复用），每步把模块 `ModuleResult.derived` 合并进去；后续模块通过 `inputs` 读取已声明的键。当前键为 `phase_impact`（第 1 步 05 输出，第 6 步 09 以 `inputs.cycle.phase_vector` 读取）与 `event_intensity`（07 的 `applyEvent` 输出，09 与 06 读取；`updateStress` 不输出该键）。`derived` 不写入 `state`、不进 `moduleResults` 的持久化投影、不进 `diagnostics`；未知键忽略并追加 `UNKNOWN_DERIVED_KEY`。**时间片重算（§5.5 的细分分支）与 `moduleResults` 同步回滚**：由于 `derived` 由每次 `runPipeline` 调用重新构造，重算时天然不会残留旧值，无需单独回滚；实现不得把 `derived` 挂在 `advance` 外层复用。缺 `phase_impact`（05 降级时省略该键）时 09 按 09 §5.6 的 `MISSING_CYCLE_DATA` 处理（全 0 向量），不得用 `state.cycle` 反推。

每个模块返回 `ModuleResult`；协调器做六件事：

1. 校验返回形状（缺 `contributions` 或 `reason_codes` 超过 16 条 → `MODULE_FAILED`）；
2. 校验 `interface_version === 1`，否则 `MODULE_FAILED`；
3. 校验 `warnings` 与 `reason_codes` 均为字符串数组且各不超过 16 条；
4. 校验数值范围与变化上限（见 00 §7.3 / 本文 §5.6）；
5. 把本次 `ModuleResult` 追加到 `moduleResults`（`contributions` 的合并由 `aggregateDiagnostics` 同键累加完成）；
6. 随结果记录 `elapsed_ms`，供 `module_ms` 汇总。

### 5.6 变化上限校验（协调器统一执行，不依赖模块自觉）

| 字段 | 普通上限（裁剪） | 高严重度上限（裁剪） | 硬上限（断言） |
| --- | --- | --- | --- |
| `mood.*` 单维 | 0.06 | 0.12 | 0.15 |
| `regulation.*` | 0.05 | 0.05 | — |
| `sleep.sleepiness` | 0.20 | 0.20 | — |
| `stress.level` | 0.30 | 0.30 | — |

"高严重度"判定：本次事件 `intensity >= 0.7`。处理分两类：

- **裁剪档**：`mood.*` 单步 `|delta|` 超过 0.06（普通）或 0.12（高严重度）但未达 0.15，以及 `regulation.*` / `sleep.sleepiness` / `stress.level` 超过各自上限时——裁剪到上限并追加 `CLAMPED_DELTA` 警告，不抛错（数值保护而非调用错误）。
- **断言档**：`mood.*` 单步 `|delta|` 超过 0.15 时**不裁剪**，抛 `MODULE_FAILED` 并回滚事务。该断言与 09 §5.3 的第二道硬边界是同一条防线。**它只能发现 `limit` 被改大（>0.15）或 `clamp` 被绕过**；"某来源绕过 alpha 或权重被改大"会被 0.06/0.12 裁剪吸收，表现为 `CLAMPED_DELTA`，**不触发该断言**（与 09 §5.3 口径一致）。09 会在模块内先行断言，协调器端是同一条断言的兜底，正常计算永远不应触发。

### 5.7 并发与乐观锁

协调器不直接存取存储，但必须提供纯函数形式的版本校验：

```js
export function checkVersion({ expectedVersion, actualVersion }) {
  if (expectedVersion !== actualVersion) {
    const e = new Error('state_version conflict');
    e.code = 'STATE_VERSION_CONFLICT'; e.retryable = true;
    throw e;
  }
}
```

调用方（04/12/13）负责重读后重试，最多 2 次，退避 200ms / 600ms；仍失败返回 `STATE_VERSION_CONFLICT`。

**同一 `character_id` 的推进必须串行。** 协调器导出一个 `createMutex()`，适配层用它把"读-算-写"包起来；纯函数核心本身不加锁。

### 5.8 版本迁移

- `migrate(state, target)` 必须逐级执行：1→2→3，不允许跳级。
- 每个迁移函数签名 `(state) => newState`，必须幂等（对已迁移状态再执行不变）。
- 缺失 `schema_version` 视为损坏 → `INTERNAL`，不猜测。
- `state.schema_version > SCHEMA_VERSION` → `STATE_VERSION_CONFLICT`（需要升级引擎）。
- 每次迁移后必须 `normalizeState` 再 `validateState`。

## 6. 边界与错误

| 场景 | 处理 | 错误码 |
| --- | --- | --- |
| `now` 缺毫秒或无 `Z` | 拒绝 | `INVALID_TIME` |
| `timezone` 非 IANA | 拒绝 | `INVALID_REQUEST` |
| 数值 `NaN`/`Infinity` | 拒绝（不默默改 0） | `INVALID_REQUEST` |
| `state_version` 非整数或 < 0 | 拒绝 | `INVALID_REQUEST` |
| `schema_version` 未知 | 拒绝 | `INTERNAL` |
| 模块返回缺少 `contributions` | 回滚 | `MODULE_FAILED` |
| 模块抛错 | 回滚，`state_version` 不变 | `MODULE_FAILED` |
| 回拨 > 5 分钟 | 钳制 + 警告 | 成功 + `CLOCK_REGRESSION` |
| 离线 > 180 天 | 4320 步 + 粗推进 | 成功 + `LONG_OFFLINE_COARSE` |
| `elapsed` 为 0 但有事件 | 仍执行流水线（事件生效） | 成功 |
| 迁移失败 | 不改动原状态 | `INTERNAL` |

## 10. 禁止事项

1. 禁止在 `lib/core` 内引入任何 npm 依赖。
2. 禁止用 `new Date()` 解析时间后自行拼字符串；必须走 `parseTime` / `toIso`。
3. 禁止手写时区偏移（如 `+8*3600*1000`）。
4. 禁止无上限循环推进时间。
5. 禁止在协调器中实现具体的周期/睡眠/情绪公式。
6. 禁止让模块返回值直接覆盖整个状态（必须按模块归属字段合并）。
7. 禁止静默把非法数值改成 0。
8. 禁止修改 `00`；需要新字段时走契约变更流程。

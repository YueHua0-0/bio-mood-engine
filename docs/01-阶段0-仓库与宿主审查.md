## 1. 背景与目标

本项目的最终形态是一个 WeChatAgent 插件（`plugin.json` + `index.mjs` + `lib/**`），内部嵌入纯函数计算核心。但在写任何接入代码之前，必须先证明以下四件事，否则后续 14 份任务书的前提可能全部错误：

1. 插件确实装在 **WeChatAgent（ZIP / API v2）** 侧，而不是 DSH 侧；
2. 插件能在微信消息链路中获得足以调用引擎的事件与上下文；
3. 8 MiB / 16 MiB / 单个 4 MiB 等体积限制的真实作用层级；
4. 插件的存储、执行时间、并发、网络能力与降级手段。

本任务书只负责"把事实查清并留下证据"，不负责设计算法。

### 1.1 已知事实（来自 API v2 文档，可直接引用，但仍需在仓库中定位代码证据）

| 编号 | 事实 | 已知来源 | 需补充的证据 |
| --- | --- | --- | --- |
| F01 | ZIP 上限 8 MiB，解压后 16 MiB，单文件 4 MiB，最多 128 个条目、8 层目录、压缩比 ≤500 | API v2「包目录与文件要求」 | 宿主中执行该校验的函数与常量名 |
| F02 | 入口固定 `index.mjs`，Node ESM，无需 `package.json`，禁止 `node_modules` | API v2 同上 | 子进程启动代码位置 |
| F03 | 插件是**独立 Node 子进程**，V8 旧生代堆 96 MiB；是故障隔离而非 OS 沙箱 | API v2「可选钩子与生命周期」 | 子进程 spawn 参数 |
| F04 | `setup(api)` 必须 2 秒内完成；禁止初始化阶段发网络请求或启动长期任务 | API v2「注册模型工具」 | 超时实现位置 |
| F05 | 工具每次最长 8 秒；每轮最多调用 3 次插件工具；结果上限 64 KiB，交给模型最多 12,000 字符 | API v2 | 超时/截断实现位置 |
| F06 | `before-context` / `after-response` 每插件每类钩子 800 ms，一类钩子总预算 2 秒；钩子只能读 storage/history | API v2 | 钩子调度实现位置 |
| F07 | `ctx.storage` 按"账号 + 插件 + 聊天"隔离，单账号单插件合计 256 KiB，键名 1–64 位 `[A-Za-z0-9_-]` | API v2 | 配额校验实现位置 |
| F08 | `ctx.fetch` 仅公开 HTTP(S) GET，不支持自定义头/体，拒绝本机与内网，`maxChars` 256–32000，`timeoutMs` 100–7000 | API v2 | fetch 过滤器实现位置 |
| F09 | `ctx.reply` 每轮最多 3 条、合计 12,000 字符；动作与每日计划不支持 `ctx.reply` | API v2 | 回复队列实现位置 |
| F10 | 插件可导出 `activate()`、`hooks`、`schedule`；无 MCP 注册、无任意文件系统 API、无原生图片发送 | API v2 | 能力注册表实现位置 |

> 说明：F01–F10 是**文档层证据**，阶段 0 要补的是**代码层证据**。文档与代码冲突时以代码为准，并在报告中标注冲突。

### 1.2 目标

- 产出一份可被其他 Agent 直接引用的《架构审查报告》，所有结论带 `文件路径:行号` 或 `命令 + 输出`。
- 产出一份《宿主约束表》，把预算换算成引擎可用的实际额度（例如"一次工具调用中，引擎计算预算 ≤ 4 秒"）。
- 给出"内嵌核心 / 远程 HTTP"两种模式的决策矩阵与推荐结论。

### 1.3 非目标

- 不实现任何 `lib/**` 业务代码。
- 不修改宿主仓库任何源码、构建脚本或上传限制。
- 不安装插件、不改动用户已安装的插件、不写宿主数据库。
- 不对 8 MiB 限制"想办法绕过"；只定位与记录。

## 2. 审查范围

### 2.1 必查清单（逐项打勾，缺一不可）

| 编号 | 审查项 | 期望产出 |
| --- | --- | --- |
| A1 | 插件加载入口与目录解析（`index.mjs` 如何被找到） | 函数名 + 路径 + 行号 |

| A15 | 现有仓库中可复用的工具函数（时间、校验、日志、哈希） | 清单 |

### 2.2 A9 是阶段 0 的最高风险项

API v2 文档只描述了"模型按需调用工具"和两个钩子，**没有描述"每条微信消息都触发插件"的订阅式机制**。因此必须查清：

- 若存在消息级钩子/事件：记录名称、触发时机、可用字段、预算。
- 若不存在：则"状态推进"只能发生在
  1. 模型调用工具时（`tools`），或
  2. `before-context` 钩子被调用时（只读，不能写 storage），或
  3. `schedule` 每日计划（时间粒度粗，且不支持 `ctx.reply`）。

若最终结论是"不存在消息级订阅"，则必须在报告中明确写出对引擎的四条影响：

1. 状态推进是**惰性**的：每次工具调用时按 `elapsed` 补算，而不是实时；
2. 睡眠期间能否"延迟交付"取决于宿主是否提供队列/延迟发送能力，需单独确认；若无，11 的 `queue_until_awake` 只能退化为"唤醒后首次推进时补发一条摘要"，不得承诺准点送达；
3. `before-context` 只能读，不能写，因此**不能**在该钩子内推进状态；只能在工具里推进；
4. 07 的 `long_silence`（>6 小时无事件）检测精度取决于推进频率：无消息级订阅时，只能在下一次工具调用或管理员 `tick` 时被发现，实际触发时间可能晚于 6 小时。报告中必须写明该偏差来源，并说明是否需要宿主定时任务；不得声称"实时检测"。

结论不确定时写"待验证"，并给出验证命令，不得猜测。

## 3. 决策矩阵：内嵌核心 vs 远程 HTTP

审查完成后按下表打分（1–5 分，分数越高越有利），加权求和：

| 维度 | 权重 | 内嵌核心 | 远程 HTTP | 说明 |
| --- | --- | --- | --- | --- |
| 部署复杂度 | 25% | | | 内嵌为单 ZIP；远程需进程守护/域名/证书 |
| 体积可行性 | 20% | | | 核心纯 JS 预计 < 1 MiB，远低于 8 MiB |
| 可用性/故障域 | 20% | | | 远程断网即不可用，需缓存快照 |
| 延迟 | 10% | | | 工具总预算 8 秒，本地无网络往返 |
| 隐私 | 15% | | | 内嵌不出本机；远程需传输聚合状态 |
| 可运维性 | 10% | | | 远程可热更新参数、集中日志 |

**推荐基线（D2）**：默认内嵌；远程仅作为同一核心的第二个部署壳。若审查发现"插件无法读取消息到达事件"或"storage 256 KiB 不足"，再评估远程模式，但**不得因此改变核心的纯函数契约**。

### 3.2 运行时预算表（把宿主预算换算成引擎预算）

| 宿主预算 | 数值 | 引擎预留 | 可用于引擎计算 |
| --- | --- | --- | --- |
| 工具单次执行 | 8 s | 序列化/存储/回复 2 s | **≤ 5 s**（目标 P99 ≤ 300 ms） |
| `setup()` 初始化 | 2 s | 禁止网络 | 只做注册，无重计算 |
| 钩子单次 | 800 ms | 读 storage ≤ 200 ms | 只做读取与格式化，不推进状态 |
| 单插件并发 | 未知，需查 | — | 同一 `character_id` 写入必须串行 |
| V8 旧生代 | 96 MiB | 状态 JSON < 2 MiB | 禁止全量历史载入内存 |

## 5. 边界与错误

| 情况 | 处理 |
| --- | --- |
| 找不到某项实现（例如打包在二进制里） | 标"待验证"，写明推断依据与影响范围 |
| 文档与代码冲突 | 以代码为准，报告"冲突"章节，列出两处位置 |
| 仓库体积过大无法全量读 | 先用关键词检索（`8 MiB`、`ZipFile`、`MAX_ZIP`、`spawn`、`before-context`、`storage`），再精读命中文件 |
| 需要运行宿主才能验证 | 允许在**测试环境**运行，不得连接真实微信账号；不得安装到生产 |
| 需要读取用户数据 | 禁止。只用测试账号/测试群 |

审查 Agent 不得因为"查不到"而编造结论；本阶段允许出现"待验证"，但 G0 关口不允许关键项（A1/A3/A4/A7/A8/A9）为"待验证"。

## 8. 禁止事项

1. 禁止为了让体积达标而删除文档、测试或改动宿主的校验逻辑。
2. 禁止把"外部服务"当成绕过 8 MiB 的默认答案；必须先用证据判断限制层级。
3. 禁止在报告中把推断写成事实，禁止伪造命令输出。
4. 禁止修改宿主仓库、安装插件到生产账号、读取真实聊天记录。
5. 禁止在本阶段编写 `lib/**` 业务代码。
6. 禁止引入任何 npm 依赖来"方便审查"。

## 1. 冲突报告 C-06-01：紧急唤醒数据通路断裂

**冲突位置**：06 §4.2 / §5.4、02 §5.5、00 v1.7.5（§4.2）、10 §5.6

**冲突内容（逐字引用）**：

- 06 §4.2：`inputs.event` / `urgent` …「本次事件（只读 `event_type`、`intensity`）与紧急标记（阻断入睡）」
- 06 §5.4：`sleeping → waking_up`｜「`now ≥ planned_wake_at`，或 `inputs.urgent_interrupt === true`（来自 11 的 `urgent_interrupt`）」
- 02 §5.5 固定顺序：「2 sleep … 4 event … 8 delivery -> {delivery} // 只读 state + config，不写 state」
- 00 v1.7.5：「02 严格读 `derived.event_intensity`，不得回退到原始 `event.intensity`」（该值在第 4 步由 07 产出）
- 10 §5.6：sleeping 时 `should_reply=false`，「优先于一切行为倾向」

**三处不一致**：

1. 06 的 `urgent` 与 `urgent_interrupt` 是两个名字、两种语义（阻断入睡 / 强制唤醒），06 §4.2 只列了前者，02 对两者的来源都未定义。
2. `urgent_interrupt` 由第 8 步的 11 产出，消费它的 06 在第 2 步，同一次 `advance` 内无法传递。
3. 06 判定打断要用事件强度，强度第 4 步才算出，第 2 步拿不到合法值。

**复现条件**：状态 sleeping、`wake_cost ≤ 0.85`，收到 conflict（`urgency=1.00`）。11 返回 `urgent_interrupt` 且 `wake_candidate=true`，但同一次返回里 `sleep.state` 仍为 sleeping，10 给出 `should_reply=false`。15 的 E03 受阻。

**影响模块**：02、06、07（强度提前）、11、10、15（E03 断言）、`assembly.shape.json`（触发 W3-3）

**建议方案**：

- **A**：02 最后一轮 `runPipeline` 做两遍。第一遍得出 `derived.event_intensity` 与 11 的策略；若为 `urgent_interrupt`，用 rng 快照回滚，把 `inputs.sleep.urgent_interrupt=true` 与事件强度传给 06，重跑下游。机制与 02 的时间片细分同类。06 里两个字段拆开命名并补入 §4.2。
- **B**：接受延迟一次推进，`urgent_interrupt` 仅为建议；10 在该策略下覆盖 `sleep_constraint`。改动小，但本次调用内紧急打断不生效。
- **C**：调整流水线顺序，事件强度与交付预判整体提前。改动面最大，不推荐。

**裁决**：方案 A（2026-11-10 正式裁决；此前倾向同为 A）。

**A 的实施细节（裁决口径）**：

1. 02 §5.5：事件那一轮先调用 11 的纯函数预判交付策略；预判为 `urgent_interrupt` 时，用 `rng` 快照回滚，把紧急标记与合法事件强度传给 06，再重跑下游。
2. 对外返回的 `delivery` **保留预判结果**；第二遍只用于更新 `state` 与 `behavior_context`，**不得覆盖 `delivery`**。否则 06 转为 `waking_up` 后 11 会重算成 `deliver_now`，15 的 E03 无法通过。
3. 06 §4.2：`urgent`（仅阻断入睡）与 `urgent_interrupt`（仅强制唤醒）拆开命名，写清来源。
4. 06 打断判定使用的事件强度必须来自 07 的 `derived.event_intensity`，不得读原始 `event.intensity`。
5. 同步文档：02 §5.5、06 §4.2/§5.4、15 E03、`assembly.shape.json`（触发 W3-3）、00 补一条版本记录。

**验收**：

- E03：返回 `delivery.policy = urgent_interrupt`、`sleep.state = waking_up`、`state_version` 只 +1。
- 回滚重跑不得重复消耗随机数：同一事件的 rng 计数器与单遍路径一致。
- T33 装配形状测试通过。

**执行顺序**：必须在 C-06-02 的仿真结果出来之后动手，避免两边测试数据混淆。

**若不处理**：紧急事件在睡眠中永远晚一次推进才唤醒；无消息级订阅时，这个「一次」可能是数小时。

**状态**：已验证（方案 A；`tests/unit/e03_urgent_interrupt.test.mjs` 2/2 通过）

## 2. 冲突报告 C-06-02：打断态困倦度口径矛盾

**冲突位置**：06 §5.2 / §5.3 / §5.5

**冲突内容（逐字引用）**：

- §5.2：「打断态（interrupted）：`s' = min(1, s + 0.02*Δt_h)` // 被打断会略微更清醒，不衰减」
- §5.3：「困倦度仍按睡眠态曲线推进（§5.2）」
- §5.5：「打断期间 sleepiness 按睡眠态曲线（目标 0.15）推进。」

§5.2 说上升，§5.3 与 §5.5 说向 0.15 衰减。

**复现条件**：任意 `sleeping → interrupted` 后 15 分钟，评估 `interrupted → sleeping`（`sleepiness ≥ 0.60`）还是 `→ waking_up`。

**附带发现（估算，待仿真验证）**：睡眠态按 `0.15 + (s-0.15)·e^(-Δt_h)` 衰减。假设入睡时 `s≈0.8`，约 22 分钟后降到 0.60 以下。两种口径下夜间打断后都很难满足 `≥ 0.60`，续睡分支近乎不可达，几乎每次打断都走 `waking_up`，与规划书 §4.5「继续睡眠 / 短暂醒来 / 完全清醒」三种结果不符。

**影响模块**：06，以及依赖打断次数的 `sleep_quality`、`sleep_debt`。不涉及 00 字段范围。

**建议方案**：

- **A**：采用「睡眠曲线」，改 §5.2 表格打断态一行，与 §5.3、§5.5 统一。
- **B**：采用「上升」，改 §5.3、§5.5 文字。
- **C**：续睡判定改用另一阈值（如 0.30），并用 16 的仿真跑一晚夜间打断，确认三种结果都会出现。

**裁决**：方案 B + C（2026-11-10 正式裁决）。

**B + C 的裁决口径**：

- **B**：保留代码现状（打断态困倦度上升，`circadian.mjs:107-114` 不动），把 06 §5.3、§5.5 文字改为「打断态困倦度按 §5.2 上升（`s' = min(1, s + 0.02·Δt_h)`）」，不再写「按睡眠态曲线」。
- **C**：续睡条件不再用 `sleepiness ≥ 0.60`，改看 `recovery_progress` 或 `sleep_debt`；阈值不预先定数，先用 16 的仿真跑一晚夜间打断（入睡后不同时刻被打断）再定。
- **同步文档**：06 §5.4 转换表、§5.5；14 / 16 中依赖续睡分支的用例。
- **验收**：仿真中「续睡 / 短暂醒来 / 完全清醒」三种结果都出现；不得出现几乎每次打断都走 `waking_up` 的分布；00 的字段范围与枚举不变。
- **执行顺序**：先做本条（只改 06，与 C-06-01 互不依赖）。

**若不处理**：实现者各选一种口径，测试按各自理解写，集成时才暴露；续睡分支即便实现正确也基本不触发。

**状态**：已验证（方案 B + C；`tests/simulation/night_interrupt.test.mjs` 通过：resume=3 / giveUp=1 / plannedWake=1 / wokeNaturally=2）

### P-12-04 · 413 的连接中止方式

**旧问题**：交底要求「`req.destroy()`」，但未读 body 时 destroy 会 RST 并丢掉 413 响应。

**代码**：`lib/api/validate.mjs:84-95`（超限即 `pause` 并拒绝）

```js
req.on('data', (chunk) => {
  if (settled) return;
  const buffer = asBuffer(chunk);
  size += buffer.length;
  if (size > limit) {
    req.pause();
    finish(reject, contractError('PAYLOAD_TOO_LARGE', `body exceeds ${limit} bytes`, { reason: 'body_too_large' }));
    return;
  }
  chunks.push(buffer);
});
```

`lib/api/handler.mjs` 的 `sendJson(..., { close: status === 413 || status === 415 })`：回 413 时带 `Connection: close`，由 Node 在响应结束后关闭连接。**状态**：已验证。

**裁决**：接受 `req.pause()` + 413 + `Connection: close`，不用显式 `req.destroy()`。附加三条：①有 `Content-Length` 且超限，读 body 前直接 413+close；②无 CL / 分块读取中超限，pause 后 413+close；③兜底定时器 `unref()`，响应结束后 socket 未关则到期 destroy，防连接泄漏。A06 须断言客户端收到 413（非 ECONNRESET）且连接随后关闭；12 §5.2 写明原因；响应写出后若缓冲区仍有未读数据仍可能 RST，须实测通过才可改「已验证」。

**实施（三条均已落地）**：

```js
// validate.mjs：① 读 body 前预判 Content-Length
const declared = Number(req.headers?.['content-length']);
if (Number.isFinite(declared) && declared > limit) {
  req.resume();
  return Promise.reject(contractError('PAYLOAD_TOO_LARGE', `body exceeds ${limit} bytes`, { reason: 'body_too_large' }));
}

// handler.mjs：③ 兜底销毁，unref 不阻止进程退出
if (status === 413 || status === 415) {
  const timer = setTimeout(() => { if (!req.socket.destroyed) req.socket.destroy(); }, 2000);
  timer.unref?.();
  res.on('close', () => clearTimeout(timer));
}
```

A06 拆为两条路径：带 `Content-Length`（①）与 `chunked: true` 无 CL（②），均断言 `413`、`connection: close`、无 `socketError`。12 §5.2 与 §6.0 第 6 步已写明「不得直接 destroy，否则客户端收到 ECONNRESET」。

### P-16-03 · `Pcg32.fastForward` 线性快进导致 365 天仿真 O(n²)（已验证）

### P-13-21 · 状态页时钟显示（已验证）

**现象**：插件状态页只有两个时间字段——页头「更新于」与睡眠卡「计划醒来」。三处渲染缺陷都会让它们看起来像"时钟坏了"：

1. `timeText()` 直接 `new Date(iso).toLocaleString('zh-CN', …)`，用的是**查看者本地时区**，而页面标签同时显示 `state_summary.timezone`。宿主进程或浏览器时区与角色时区不一致时，两个时间整体偏移若干小时，而时区标签仍写角色时区。
2. 选项写 `hour12: false` 而未固定 `hourCycle`。02 §4.2 已记录该写法在部分引擎会解析为 `h24`、把零点输出成 `24:00`；`lib/core/clock.mjs` 用 `hourCycle:'h23'` + `%24` 防过，页面没有。
3. 「更新于」只渲染时分秒，不带日期。状态只在 `observe` / `tick` 时推进，数天未推进的旧状态会显示成"今天 17:00:00"，与当前时间不符，极易被判成时钟错误。

**修复**：`timeText(value, { withDate, withSeconds, timeZone })`：

- 传入 `summary.timezone` 作为 `timeZone`，时间按角色时区呈现；时区名非法时 `try/catch` 去掉该选项回退本地，避免整页因 `RangeError` 空白。

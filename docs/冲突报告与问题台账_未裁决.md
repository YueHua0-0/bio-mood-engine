## 0. 交接规则（防遗漏）

1. **编号唯一**：所有问题用 `C-xx-nn`（契约冲突）或 `P-xx-nn`（非冲突问题）编号；两个文件的编号不得重复，沟通时只说编号，不复述。
2. **状态只有六种**：待裁决 → 已裁决 → 契约已改 → 代码已改 → 已验证 / 驳回。
3. **谁改状态**：线上 AI 只改到「已裁决」；桌面 agent 完成修改后改「代码已改」，并贴出测试命令与输出；验证通过才允许改「已验证」。
4. **关闭即迁移**：条目转为「已验证」或「驳回」时，同一次修改把主表行、详情、索引与验证证据完整迁移到已验证文件，不在本文件保留重复副本。
5. **新问题先登记再讨论**：发现新问题，先在 §1 追加一行并在 §2 附证据，再去问线上 AI；线上 AI 的回答必须引用编号。
6. **登记必带证据**：新增或裁决任何条目时，§2 必须附「文件:行 + 原样代码段 + 现状判断」；纯文档/契约类条目附契约原文逐字引用（含行号）。缺证据视为登记不完整，不得进入裁决流程。
7. **未关闭项阻塞**：存在「待裁决」的 C 类问题时，相关模块不得进入下一波次。
8. **每轮只贴当前文件**：新对话只把本文件交给线上 AI；已验证文件仅在追溯历史时按需读取，不再整篇粘贴。
9. **汇报必带台账**：桌面 agent 每次汇报末尾必须附 §4 的「台账变更表」；没有变更也要明确写出。

### P-15-09 · T12 纯 chunk 墙钟门禁的机器依赖（已裁决 A，代码已改）

**原状态说明**：详情标题曾写「待裁决」；主表后续已记录「已裁决（A）· 代码已改」。拆分时以较新的主表状态为准，以下保留原始证据与裁决。

**触发条件成立**：裁决 P-15-08 时已预先登记「若 CI 首次跑挂 T12，则登记新编号，方向为隔离运行 + 固定采样取中位数，不得放宽阈值」。首次 CI 即挂在 T12，故登记本项。

**原始证据**

| 环境 | 测量方式 | 结果 |
| --- | --- | --- |
| GitHub `ubuntu-latest`（Node 24） | 单次 2000 次采样，无预热 | **0.5517 ms/次**，超 0.4 门禁 38%，用例耗时 1109 ms |
| 本机 Node `v24.19.0`，同测试五轮 | 5 轮 × 2000 次，丢弃预热，取中位数 | min **0.3638** / 中位 **0.4507** / max **0.7537**，抖动约 2.1× |
| 本机历史三轮全量 | 单次采样 | 0.3928 / 0.4052 / 0.4082 |

**已做的测量口径调整（不改阈值）**：`baseline.test.mjs` 的纯 chunk 段改为 5 轮、丢弃一轮预热、取中位数，并输出 min/中位/max 诊断；`.github/workflows/test.yml` 在两个 job 前增加 `lscpu` / `nproc` / `uptime` 记录，用于区分「机器慢」与「负载高」。

**为什么只做到这里**：本机五轮最小值 0.3638 已低于 0.4，而中位 0.4507 高于 0.4，说明该指标不是稳定的单值，而是随负载在 0.36–0.75 之间漂移。取中位数只是把噪声后移，不能消除跨机差异；若 CI 单核持续慢于本机，中位数仍会超限。

**裁决 A（2026-11-11）**：不采用「CI 只记录」或「放宽阈值」。chunk 门禁改为**同进程归一化比值**：`每步耗时 / nextU32 每次耗时`，5 轮丢弃预热取最小比值，门禁 ≤3400（≈ 原 0.4 ms × 1.25 余量，且 `nextU32` 与 chunk 同进程同负载测量，主频与负载在比值中抵消）。4320 步离线推进同步改为连续 3 轮取最小值，预算仍为 2 s。

**实施后本机数据**：三次单跑 chunk 最小比值 **2572 / 3040 / 3121**，全部低于 3400；同一台机器上 4320 步在 43% 持续后台负载（python 进程累计 CPU 14 545 s）下为 **2365–3092 ms**，而同等代码在空载时记录为 **1377.9 ms**，判定为环境负载而非代码回归。因此本地绝对耗时不再用于标定，改由 CI 复跑判定。

**仍未关闭**：CI 复跑结果未取得（上一轮 run `43040633080` 仍红，原因为绝对值门禁）。P-15-08 的两次连续绿色与 10 轮全绿仍依赖 CI。

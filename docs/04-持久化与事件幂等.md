## 1. 背景与目标

引擎其余部分都是纯函数，只有存储是有状态边界。一旦出现“状态已写、事件未记”或“重复事件重复推进”，前面所有模块的可复现性都会失效。本模块只做三件事：统一仓库接口、单事务推进、幂等去重。保存的全部内容是**虚构角色状态模拟**（周期、睡眠、调节、情绪均为模拟值），不含真实人体医学数据，不用于诊断、治疗或现实健康预测。

### 1.1 宿主存储的硬限制（来自 01 的 G0 结论）

| 项 | 事实 | 直接影响 |
| --- | --- | --- |
| 隔离粒度 | 账号 + 插件 + 聊天 | **没有账号级共享存储**，跨聊天不可见 |
| 配额与键名 | 单账号单插件 256 KiB；键名 1–64 位 `[A-Za-z0-9_-]` | 不能把 `character_id` 拼进键名 |
| 原子性 | 宿主只保证单键读写完整 | 多键事务必须用写前日志 + 补偿 |

**结论**：权威状态只能落在某个聊天作用域内，其他聊天只读缓存快照，不能推进状态。

## 5. 算法与规则

### 5.1 键名方案

| 键 | 内容 | 上限（见 00 §11.5） | 写入者 |
| --- | --- | --- | --- |
| `state` | 完整 `CharacterState`（00 §3） | 8 KiB | 事务提交 |
| `evlog` | 事件日志环形数组（最近 200 条） | 16 KiB | `appendEvent` |
| `idem` | 幂等索引（300 条 / 7 天） | 32 KiB | 事务提交 |
| `meta` | `schema_migrations`、`state_backup`、`snapshots`(最多 12 条**摘要**)、`tx_journal`、`rollback_state` | 24 KiB | 适配器 |
| `cfg` | 最近一次有效配置快照 | 4 KiB | 初始化/配置变更 |
| `history`（仅文件/SQLite） | 30 天逐小时采样的状态历史 | 不计入 64 KiB，但单独 ≤2 MiB | 采样任务；**插件模式禁止该键**，`get/set/delete('history')` 一律 `INVALID_REQUEST` |

键名只用固定字面量（3–5 字符），子字段放在值内部；禁止把 `characterId`、时间戳拼进键名（超出 64 位且无法枚举）。

**首次初始化的写入口径（交叉引用 13 §5.2，P-13-04）**：空白库的 `state` 只能由 13 的 `observe` 在**同一个 `repo.transaction()` 内**写完 `state`/`evlog`/`idem`；`saveState(init, 0)` 只是该事务内的临时基础版本，最终版本统一由 `t.putState()` 提交。禁止“先事务外初始化、再开启事务推进”的两段式写法——那会绕过本模块的迁移日志与回滚保证。

### 5.2 体积预算与淘汰

**唯一预算表在 00 §11.5，本模块只负责执行，不得自定义数字。**

| 对象 | 硬上限 | 稳态目标 | 处理 |
| --- | --- | --- | --- |
| 状态 JSON | 8 KiB | ≤4 KiB | 禁止淘汰，超限报 `STORAGE_FAILED` |
| 事件日志 | 16 KiB / 200 条 | ≤10 KiB | 按时间淘汰最旧 |
| 幂等索引 | 32 KiB / 300 条 | ≤20 KiB | 先按 7 天过期，再按最旧淘汰 |
| `meta`（含 12 条摘要） | 24 KiB | ≤8 KiB | 先淘汰最旧摘要，再淘汰 `tx_journal` 残留；迁移窗口内允许接近 24 KiB（`state_backup` ≤8 KiB），迁移结束立即回落 |
| `cfg` | 4 KiB | ≤2 KiB | 禁止淘汰 |
| 合计 | — | ≤64 KiB（配额 25%） | >64 KiB 立即淘汰；>224 KiB 硬失败 |

淘汰顺序固定为 **`meta.snapshots` → `idem` → `evlog`**，`state` 与 `cfg` 永不淘汰。每次淘汰追加 `STORAGE_EVICTED` 警告（不是错误码，见 00 §9.2.1）。单项硬上限之和为 84 KiB，仅用于崩溃恢复期瞬时峰值；稳态目标之和为 44 KiB（4+10+20+8+2）。`meta.snapshots` 每条只存 `{state_version, updated_at, summary}`（≤256 B）；完整状态只允许存在于 `state` 键，**唯一例外是迁移窗口内的 `meta.state_backup`**（≤8 KiB、成功即删、对外脱敏），其余位置（`snapshots` / `evlog` / `idem` / `cfg` / `rollback_state`）一律不得存完整状态。单条幂等记录约 100 B（24 位键 + 版本 + ISO 时间），300 条约 30 KiB，落在 32 KiB 上限内。

**淘汰分两类，互不替代，且都只在写路径、都持该角色的锁执行**（只读路径 `loadState({readOnly:true})` 不参与）：

1. **跨键总量淘汰**（仅当五键合计 >64 KiB）：严格按 `meta.snapshots → idem → evlog` 顺序，单次 ≤64 条，未收敛的留到下一次写路径；每次最多 3 次批量 `set`，不得逐条写键。`state` / `cfg` 永不淘汰。
2. **单键写前收缩**（仅写路径，为即将写入的键腾空间）：只收缩该键本身到写目标以下（`evlog ≤14 KiB`、`idem ≤30 KiB`，目标低于 16 / 32 KiB 硬上限，预留一次 append 的空间）；不跨键、不计入 64 条上限。

单键收缩是为了避免"键恰好等于硬上限 → 下一次 `appendEvent` 必失败"，**不改变**跨键淘汰顺序，也不会先于 `meta.snapshots` 去删 `evlog` 而违反第 1 类的固定顺序。两类淘汰都在 `ensureReady()` 内、`prepareWritePath()` 的淘汰段执行，并由仓库锁串行化（§5.4）。S08 断言跨键总量收敛，S35 断言单键收缩后 append 成功，S37 断言维护写入不在事务补偿范围内。

**账号级配额（不可测量上界）**：上面的预算检查只能覆盖**本聊天**的五个键。宿主配额是"账号 + 插件"合计 256 KiB（API v2:148），多个聊天的 `ctx.storage` 共享这一上界，插件无法读取其他聊天占用了多少，因此本模块把 **256 KiB 视为不可测量上界**，不尝试做账号级协调。当前安全性由**单写者不变式**保证：只有 `primary_chat_id` 对应的聊天可以写键，非主聊天 `saveState` 返回 `DEGRADED`、`appendEvent` 丢弃、`transaction` 抛 `DEGRADED`（13 §5.5），因此账号占用 = 主聊天占用 ≤84 KiB（单项硬上限之和）<256 KiB。**若未来启用 `AccountScopedStorageRepo` 或多写者，必须先新增账号级预算协调，否则 256 KiB 会被静默突破**（债务 D-5，见 `architecture_audit.md` §9.1）。

**插件模式的键集合与单键校验**：`createChatScopedRepo` 只允许 `state` / `evlog` / `idem` / `meta` / `cfg` 五个键；任何 `get` / `set` / `delete` 命中其他键（包括 `history`、把 `snapshots` 当顶层键）→ `INVALID_REQUEST`。`set` 前按 `Buffer.byteLength` 校验**单键硬上限**（8 / 16 / 32 / 24 / 4 KiB），越界抛 `STORAGE_FAILED`（`state` 用 `details.reason='state_too_large'`，其余键只带 `details.key`，不发明新的 `reason` 字符串，见 00 §11）；这样零额外读取，合计 84 KiB 由淘汰保证。`history` 只在文件 / SQLite 模式可用（§5.1），插件模式既不允许写入也不保存 30 天历史。

### 5.3 事务

实现 00 §11.0 的 `Transaction` 契约，回调只能通过 `tx` 操作键：

```text
tx = repository.transaction(async (t) => {
  cur  = await t.getState(characterId)                  // 读版本
  dup  = await t.getIdempotency(key)                    // 查幂等
  if (dup) return { duplicate: true, ...dup }           // 不写任何键
  rng  = RandomProvider.fromPersisted({ random: cur.state.random, character_id: characterId }) // 00 §11.4：每次 advance 前创建
  r    = advance({ state: cur.state, event, now, rngProvider: rng, config }) // 纯函数；返回的 r.state.random 已含写回计数器
  await t.putState(r.state, cur.version)                // 写状态，version+1
  await t.appendEvent(eventRecord)                      // 写事件
  await t.appendIdempotency(idemRecord)                 // 写幂等
  return { duplicate: false, state_version: cur.version + 1,
           delivery: r.delivery, behavior_context: r.behavior_context }
})
```

**读失败的处置（P-14-04，裁决 A）**：底层 `get` 只在 `ENOENT` 时返回 `null`（表示键不存在，可走首次初始化）；其余读错误（权限、I/O、序列化）一律抛 `STORAGE_FAILED`，**不得**降级为“空库/默认值”，否则存储故障会被误判为首次运行并覆盖既有数据。实现见 `lib/storage/file-store.mjs` 的 `get()`。

回调抛错时按以下顺序处理（C-04-02）：

1. 丢弃内存缓冲，按 W1–W8 的补偿规则回滚已写键；
2. 回滚成功：
   - 若异常带 code 且 code !== 'STORAGE_FAILED' → **原样透传**（MODULE_FAILED / INVALID_REQUEST /
     STATE_VERSION_CONFLICT / DEGRADED 均属业务错误，调用方需要区分可重试性）；
   - 否则（无 code，或 code === 'STORAGE_FAILED'）→ 抛 STORAGE_FAILED。
3. 回滚失败：
   - 先尝试写 `meta.recovery_required = {operation, at, reason}`（该写入独立于失败的 state 写入）；
   - 再抛 `STORAGE_FAILED`，`details.recovery_required = true`；若 recovery_required 也写不进去，仅记日志。

判定"存储层错误"的依据：异常由 `tx.get/put/del/putState/appendEvent/appendIdempotency` 抛出，或 `err.code === 'STORAGE_FAILED'`。业务层抛出的错误一律透传，不得被吞成 `STORAGE_FAILED`。

**`ensureReady()` 的写入在事务边界之外（维护性写入）**：`prepareWritePath()`（校验 → 迁移 → 淘汰）在 `W1` 之前执行，不在 `W1–W8b` 的补偿范围内。`fn` 抛错时只回滚 `W1–W8b` 的写入（或根本没有进入 `commit`），**已完成的迁移与淘汰保留**。这是有意为之：迁移失败由 `state_backup` 负责（§5.6），淘汰本身幂等（删最旧条目可重复执行）。因此 S14 的"所有键保持事务前值"只覆盖 `W1–W8b`；若用例预置了"待迁移 / 待淘汰"，正确语义是"除 `ensureReady()` 的维护写入外，其余键保持事务前值"（S37 固定该边界）。

**回滚成功后必须 `throw` 原异常对象**，不得重新构造（`throw new Error(e.message)` 会丢失 `code`，S30/S31 依赖 `err.code` 原样保留）。

**中止（`signal`）的边界（v1.7.11，P1-B）**：`transaction(fn, { signal })` 的 `signal` 为可选 `AbortSignal`。检查点严格限制在 **W1 之前**与 **W1–W6 每个 `await` 之后**（含 W7 之前）；命中 `signal.aborted` 时抛内部错误 `ABORTED`（**不是** 00 §9.2 的公开码，只在 04↔12 之间传递），按上条流程回滚后抛出。**W7 写入 `phase='committed'` 之后不再检查 `signal`**：清理段（W8）照常完成，此时的中止请求只记日志忽略——已提交事务不得被撤销，否则违反 I9 的反面。S40 覆盖"未提交中止"，S40b 覆盖"W7 之后中止不生效"。

**内存权威状态始终不更新。**

#### 5.3.1 WAL 写入顺序（强制）

宿主只保证单键读写完整，多键之间没有原子性。因此固定为"两阶段 + 提交标记"：

| 步 | 操作 | 失败时的处理 |
| --- | --- | --- |
| W1 | 读取 `state` 与 `idem` | 直接失败，无写入 |
| W2 | 写入 `meta.rollback_state = sanitize(prevState)`；创建路径（库中无 `state`）写 `null` | 中止，无副作用 |
| W3 | 写入 `meta.tx_journal = {tx_id, phase:'prepared', prev_version, to_version, idem_keys:[...], evlog_event_ids:[...], created_at}` | 删除 `rollback_state` 后中止 |
| W4 | 写入 `state`（校验 `expectedVersion`） | 进入回滚（用 `rollback_state`） |
| W5 | 追加 `evlog` | 回滚状态并按 `evlog_event_ids` 删除本次追加的日志条目 |
| W6 | 追加 `idem` | 回滚状态与日志、删除本次幂等条目 |
| W7 | 改写 `tx_journal.phase = 'committed'`（提交点） | 重试 1 次；仍失败进入回滚 |
| W8 | 删除 `rollback_state`，再删除 `tx_journal` | 保留日志，下次启动清理 |

`meta.tx_journal` 字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `tx_id` | string | 本次事务唯一标识 |
| `phase` | enum | `prepared` / `committed` |
| `prev_version` / `to_version` | integer | 事务前后的 `state_version` |
| `idem_keys` | string[] | 本次写入的幂等键，回滚时据此删除 |
| `evlog_event_ids` | string[] | 本次追加到 `evlog` 的 `event_id`，回滚时据此**精确**删除；仅靠版本号会误删同版本的其他事件 |
| `created_at` | string | UTC ISO 8601 |

规则：

- **`rollback_state` 必须先于 `tx_journal` 写入**，否则崩溃后会出现"有日志、无回滚数据"。
- 提交标记只能写在 W7，不得提前；W7 之后即使清理失败也算提交成功，且**不再响应 `signal` 中止**（§5.3）。
- `tx_journal.idem_keys` 必须记录本次写入的幂等键，回滚时据此删除；仅靠版本号无法定位。
- `tx_journal.evlog_event_ids` 必须记录本次追加到 `evlog` 的 `event_id`；回滚只删这些 id。字段缺失或结构损坏时，**保守放弃删除**并写 `meta.recovery_required`（`details.reason='recovery_required'`），抛 `STORAGE_FAILED`；不得按 `state_version` 猜删——同版本可能已有其他事件。
- 事务内键操作 ≤40 次（00 §11.0）。
- 创建路径（`W1` 读到 `state` 为 null）不写 `rollback_state`（写 `null`）；回滚 = 删除已写入的 `state` 键，恢复为"不存在"。
- **管理动作（`reset_state` / `reset_seed` / `manual_cycle_correction`）失败时不自动回滚**：它们会改写 `master_seed_hex` 或整体重建状态，回滚语义不成立。失败即写 `meta.recovery_required = {operation, at, reason}` 并抛 `STORAGE_FAILED`，由管理员通过 `/v1/admin/reset` 的 `reset_state` 修复。

`sanitize(state)`：

```text
sanitize(state)：
  - 深拷贝 state；
  - 把 random.master_seed_hex 替换为 random.master_seed_id（sha256 前 8 位），并删除 master_seed_hex；
  - 其余字段原样保留（含 state_version、random.streams 的 seed_hex/counter）。

回滚时（恢复状态机使用 rollback_state 覆盖 state）：
  const { master_seed_id, ...prevRandom } = rollback_state.random;
  restored = { ...rollback_state, random: { ...prevRandom,
               master_seed_hex: currentState.random.master_seed_hex } }
  理由：普通 advance 不改种子，currentState 与 prevState 种子相同，继承无损；
        种子只从 currentState 取，其余（streams 的 seed_hex/counter）全部用 rollback_state 的；
        master_seed_id 只是脱敏替身，恢复时必须丢弃，否则 random 出现未知键、validateState 拒绝。
```

`meta.rollback_state` 是**内部快照类型，不是 `CharacterState`**：它缺 `master_seed_hex`、多 `master_seed_id`。任何代码路径都不得直接返回它、不得对它调用 `validateState`、不得把它持久化到 `state` 键以外的位置；唯一合法用法是 `restoreFromRollback(rollback_state, currentState)`，事务回滚与启动恢复共用同一实现。

#### 5.3.2 启动恢复状态机

每次 `loadState` 前先执行 `recover()`：

| 现场 | 判定 | 动作 |
| --- | --- | --- |
| 无 `tx_journal`，有孤儿 `rollback_state` | 崩在 W2 与 W3 之间 | 删除 `rollback_state`（状态未改） |
| `phase='prepared'` 且 `state.state_version < to_version` | 崩在 W4 前 | 删除本次 `idem_keys`、日志追加项，删除 journal 与 rollback |
| `phase='prepared'` 且 `state.state_version === to_version` 且幂等记录齐全 | 崩在 W7 前，实际已全部写入 | 补写 `phase='committed'`，再清理 |
| `phase='prepared'` 且 `state.state_version === to_version` 但幂等缺失 | 崩在 W6 前 | 用 `restoreFromRollback(rollback_state, currentState)` 覆盖 `state`（种子从 currentState 继承，见 §5.3.1），删除日志与幂等，再清理 |
| `phase='committed'` | 崩在 W8 清理阶段 | 直接清理 `rollback_state` 与 journal |
| journal 结构损坏 / `tx_id` 不匹配 / `rollback_state` 缺失且需要回滚 | 不一致 | 写 `meta.recovery_required`，拒绝后续推进 |
| 回滚写入本身失败 | 存储不可用 | 先独立尝试写 `meta.recovery_required`（不依赖失败的 state 写入）；仍失败则仅日志告警；抛 `STORAGE_FAILED`（`details.recovery_required=true`） |

**跨版本 journal（v1.7.7 起）**：`tx_journal` 是瞬态的——事务内创建、结束即删除，只有崩溃才会留下。v1.7.7 之前版本写入的 journal **不含 `evlog_event_ids`**，一律按"journal 结构损坏"处理（见上表末两行）：写 `meta.recovery_required`、拒绝推进。开发环境直接清空 `meta` 后重启即可；生产环境走管理员 `reset_state`。不提供"按 `state_version` 兜底删除"的兼容路径（会误删同版本的其他事件）。

`recovery_required` 存在时：所有推进请求立即返回 `STORAGE_FAILED`（`details.recovery_required=true`），只允许管理员通过 12 的 `/v1/admin/reset` 修复；**禁止**用半恢复状态继续运行。

崩溃点矩阵（必须逐点测试）：W2 后、W3 后、W4 后、W5 后、W6 后、W7 后、W8 第一删后，共 7 个点。

### 5.4 乐观锁与幂等

`saveState(state, expectedVersion)` 的两种语义：

```text
- 创建：库中无 `state` 键且 expectedVersion === 0，要求 state.state_version === 0；
  写入后仍为 0，返回 { ok:true, state_version:0 }。
- 更新：库中已有 `state` 键，要求 state.state_version === expectedVersion + 1；
  返回 { ok:true, state_version: expectedVersion + 1 }。
- 其余组合一律 { ok:false, code:'STATE_VERSION_CONFLICT' }，不写任何键。
```

- `saveState` 必须比对 `expectedVersion`；不匹配返回 `STATE_VERSION_CONFLICT`，不写任何键。调用方重读后最多重试 2 次（退避 200 ms / 600 ms），仍失败上抛；同一 `character_id` 的读-算-写由 02 的 `createMutex()` 串行化，**锁必须包住 `getState` → 计算 → `putState` 全程，不得只包写入**：单进程内最多 8 个并发 call 会在 `await` 处交错，只包写入仍会出现两方读到同一旧版本。
- 唯一键 `(character_id, idempotency_key)`；重复请求返回首次结果（12 §5.4）并标记 `duplicate:true`，`state_version` 不变。
- **锁覆盖 `ensureReady()` 的迁移段与淘汰段**：`transaction()` 只在 `W1→W8b` 持锁、`fn` 不持锁；`prepareWritePath()` 的读-校验-恢复-迁移-淘汰整段通过仓库锁串行化（P2 裁决 A）。迁移虽极低频，但"`state_backup` 兜底"只保证失败可恢复、不保证并发下迁移函数不被重复应用（A 与 B 同时读到 `schema_version=1` 会各应用一次），故不再把迁移留在锁外；`04 §5.8` 的"迁移函数必须幂等"退为兜底假设。淘汰同理：否则一方在 `W5` 追加 `evlog`、另一方在锁外删最旧条目，可能误删刚写入的事件。
- 同一 `event_id` 不同 key 视为两次请求：都推进，但 `evlog` 只保留先到的一条并发 `DUPLICATE_EVENT_ID` 警告；幂等与状态同事务写入。

### 5.5 主聊天作用域

| 场景 | 行为 |
| --- | --- |
| `primary_chat_id === chatId` | 权威作用域：读写全部键 |
| `primary_chat_id !== chatId` | 只读：`loadState` 返回本聊天缓存快照；`saveState` 返回 `{ ok:false, code:'DEGRADED', details:{ warnings:['NON_PRIMARY_READONLY'] } }`；`appendEvent` 丢弃并计数 |
| 未配置 `primary_chat_id` | **fail-closed**：所有写操作返回 `{ ok:false, code:'DEGRADED', details:{ warnings:['PRIMARY_UNBOUND'] } }`，由管理员显式绑定（12 的 `/v1/admin/reset` 或 13 的管理工具）；禁止首次调用自动抢占 |
| 已占用但非主聊天 | 只读 + `{ ok:false, code:'DEGRADED', details:{ warnings:['NON_PRIMARY_READONLY'] } }` |

`PRIMARY_UNBOUND` 与 `NON_PRIMARY_READONLY` 的区分：前者表示 `primary_chat_id` 未配置（需管理员绑定），后者表示已绑定但不是当前聊天。两者都用 `code:'DEGRADED'`，靠 `details.warnings` 区分；12 / 13 不得把两者都当成同一种降级。

`meta` 同样按聊天隔离，进程重启后无法跨聊天确认归属，**上线前必须显式配置 `primary_chat_id`**，否则只允许单聊天部署。13 的 `bind_primary` 只在当前聊天的 `meta` 生效，对其他聊天不可见；第一版不支持跨聊天发现，多聊天场景必须通过 `settings.primaryChatId` 预置。`AccountScopedStorageRepo` 仅当阶段 0 证明存在账号级存储 API 时启用，接口完全相同，`chatId` 只作为审计字段；`hostSupportsAccountScope` 为假必须抛 `INVALID_REQUEST`，不得静默降级为聊天作用域。

**账号级配额的当前缓解（D-5，v1.7.9 登记）**：宿主无"已用字节"接口，账号级 256 KiB 不可测量。当前唯一缓解是**单写者不变式**：TId 可写、非主聊天 `saveState` 返回 `DEGRADED`、`appendEvent` 丢弃，因此账号占用 = 主聊天占用 ≤ 84 KiB < 256 KiB。若未来启用 `AccountScopedStorageRepo`（多聊天共享存储）或放开非主聊天写入，**必须**先在本节新增账号级预算协调（各角色预算之和 ≤ 256 KiB 的分配与占用上报），否则 256 KiB 会被静默突破。14 不得为此写断言（无接口可测），本条仅是登记。

### 5.6 迁移、备份与保留

- `meta.schema_migrations` 记录 `[{from,to,applied_at,engine_version}]`；重复 `from→to` 直接跳过（幂等）；`schema_version === target_version` 时整个迁移 no-op，不写任何键（M05）。
- 迁移前写 `meta.state_backup = {schema_version, state, digest, created_at}`；**写备份前先校验 `Buffer.byteLength(JSON.stringify(state)) ≤ 8 KiB`**，超限直接失败并保留原状态（不得"备份写不进去就跳过备份继续迁移"，M06），返回 `STORAGE_FAILED` + `details.reason='migration_failed'`；迁移步骤执行抛错时用备份恢复、保留备份、记 `migration_failed_at` 并返回 `INTERNAL`，同时追加 `MIGRATION_FAILED` 警告。
- **读路径不迁移、不淘汰**：`loadState(characterId, { readOnly: true })` 不调用迁移执行器、不写 `state_backup`、不触发淘汰；版本落后时只返回 `warnings:['MIGRATION_DEFERRED']`，把迁移留给下一次写路径（S32）。三种只读降级码（`MIGRATION_DEFERRED` / `STORAGE_OVER_BUDGET` / `RECOVERY_DEFERRED`）的定义见 00 §9.2.1。
- `state_backup.state` 允许包含完整 `master_seed_hex`（00 §10.2.1 唯一例外）。
- 迁移成功后立即删除 `state_backup`；失败时保留并记 `migration_failed_at`，但对外输出一律脱敏为 `master_seed_id`。
- 只允许一份，≤8 KiB；不得复制到 `snapshots` / `evlog` / `idem` / `cfg`。
- `schema_version` 缺失视为损坏 → `INTERNAL`；高于引擎支持版本 → `STATE_VERSION_CONFLICT`。

| 数据 | 保留 | 位置 |
| --- | --- | --- |
| 事件日志 | 90 天 / 200 条 | `evlog` |
| 状态历史 | 30 天，每小时 1 条（仅文件/SQLite） | 插件模式只留 12 条摘要；`history` 不计入 `evlog` |
| 幂等索引 | 7 天 / 300 条 | `idem` |
| 应用日志 | 7 天或 20 MiB | 13/14 负责，04 只导出常量 |

介质：插件模式**只允许** `plugin-storage`（无文件 API）；独立 HTTP 模式默认 `file-store`（临时文件 + 同目录 `rename` 原子替换）；Node ≥ 22.5 且 `node:sqlite` 可用时可选 `sqlite-store`，不可用时回退 `file-store`，禁止退化为内存存储。`createSqliteStore({path})` 的回退目录固定为 `<path>.files`，返回对象带 `warnings:['SQLITE_UNAVAILABLE']`，其余行为与 `createFileStore({dir})` 完全一致；HTTP 服务的 `repo` 由部署方用这两种介质组装后注入（12 §5.11）。

## 6. 边界与错误

| 场景 | 处理 | 错误码 |
| --- | --- | --- |
| 状态不存在 | `loadState` 返回 `null`，由调用方初始化 | — |
| `expectedVersion` 不匹配 | 不写任何键 | `STATE_VERSION_CONFLICT` |
| 重复 `(character_id, idempotency_key)` | 返回首次结果 + `duplicate:true`（12 §5.4） | 成功（HTTP 200） |
| 写状态成功但事件写失败 | 用 `rollback_state` 回滚 | `STORAGE_FAILED` |
| 事务内抛业务错误（如 `MODULE_FAILED`） | 回滚后原样透传，不转 `STORAGE_FAILED` | 原 `code` |
| 回滚失败 | 独立写 `meta.recovery_required` 后抛出 | `STORAGE_FAILED`（`details.recovery_required=true`） |
| 状态 JSON 恰好 8 KiB | 允许写入 | 成功 |
| 状态 JSON > 8 KiB | 拒绝写入，保留旧状态 | `STORAGE_FAILED`（`details.reason='state_too_large'`） |
| 合计体积 > 224 KiB | 停止写入，只读降级 | `STORAGE_FAILED` |
| `node:sqlite` 不可用 | 回退 `file-store`（JSON + 原子写） | 成功（警告） |
| 键名超 64 位或含非法字符 | 构造期拒绝 | `INVALID_REQUEST` |
| 非主聊天尝试推进 | 返回缓存快照 | `DEGRADED` |
| 存储返回非法 JSON / 迁移失败 | 尝试备份恢复 | `INTERNAL` |

**管理重置对存储键的影响**（12 §5.8 / 13 §5.9 的存储层口径）：

| 操作 | `state` | `idem` | `evlog` | `cfg` / `meta` |
| --- | --- | --- | --- | --- |
| `reset_state` | 覆盖为契约默认值；`state_version` = 旧值 + 1（不回退 0），`created_at` 保留 | 清空 | **保留**（审计依据，90 天保留不变，并追加本次管理操作记录） | `cfg` 保留；`meta.master_seed_id` 保留；**清除 `meta.state_backup` 与 `migration_failed_at`**（迁移失败后的逃生舱，P1 修复） |
| `reset_seed` | 仅重写 `random`（五条流 `seed_hex` 重派生、计数器归零），其余字段保留 | 保留 | 保留 | `meta.master_seed_id` 同步更新；`meta.state_backup` 非空 → 拒绝（`migration_backup_pending`） |
| `manual_cycle_correction` | 仅替换 `cycle`（由调用方 `prepare` 计算），其余字段保留；`state_version` = 旧值 + 1 | 保留 | 保留 | `meta.master_seed_id` 不变；`meta.state_backup` 非空 → 拒绝（`migration_backup_pending`） |

**管理操作写入 `evlog` 的字段**（`reset_state` / `reset_seed` / `bind_primary` / `manual_cycle_correction`）：`event_type='admin_command'`（00 §2.3，基础强度 0.00、衰减档 `none`，不影响 `stress`）、`source_key='wechat:<primary_chat_id>:admin'`（满足 00 §2.1 的 `wechat:<conversation_id>:<sender_id>` 格式）、`intensity=0`、`occurred_at=now`；`event_id` 为确定性值 `adm_<sha256(character_id|operation|occurred_at)[0:16]>`（满足 00 §2.1 字符集与长度）。仓库不感知主聊天：`source_key` 默认 `wechat:admin:admin`，这是 13 未注入 `admin_source_key` 时的**兜底**；生产应由 13 传 `wechat:<primaryChatId>:admin`，否则审计时无法定位是哪个聊天触发的重置。12 若经 HTTP 触发，同样应显式传入。**`evlog` 只追加不重放**，不作为状态重建来源，因此管理记录不会影响后续推进。记录中不得含被清空的旧 `state`、种子、正文或令牌（12 §5.8 的"只写操作类型与时间"指结构化访问日志字段，`evlog` 条目按本条定义）。

管理动作**不走 `repo.transaction()`**（B 方案）：按 `state` → `idem`（仅 `reset_state` 写 `[]`）→ `evlog` → `meta` 的顺序直接写，不做 WAL 与幂等查重；失败时按 §5.3.1 最后一条处理——**不自动回滚**，写 `meta.recovery_required` 并抛 `STORAGE_FAILED`。写序固定为 `state` 先写：`state` 是权威，若先清 `idem` 而 `state` 写失败，管理员无法判断"是否已重置过"；反之 `state` 已落盘、`idem` 未清时，失败由 `meta.recovery_required` 暴露，下一次 `reset_state` 可再次清空 `idem`（S39 固定该中间态：`state_version` 已是旧值 + 1、`idem` 保留、`evlog` 无本次审计）。理由：管理动作频率低、不需要幂等去重，且 `reset_seed` 会改写种子，WAL 回滚语义不成立。

**`adminReset` 的唯一实现（v1.7.11，P1-A）**：`createRepository()` 的返回值增加

```js
adminReset(characterId, { operation, payload?, now, prepare? }) → Promise<
  {ok:true, operation, accepted_at, state_version} |
  {ok:false, code:'STORAGE_FAILED', details:{recovery_required?:true, reason?:string}}
>
```

12 §5.8 与 13 §5.9 **都只调用它**，不得各自实现键操作；HTTP 层与工具层只做参数校验与结果映射。

- `operation` 取 `reset_state` / `reset_seed` / `manual_cycle_correction`；未知值抛 `INVALID_REQUEST`。
- **时间基准是调用方传入的 `now`**（来自请求体），不从 factory 的 `clock` 读：`state.updated_at`、`evlog.occurred_at`、`accepted_at` 一律取 `now`。`clock` 不参与 `adminReset`，避免"校验用系统时间、请求体用客户端时间"的双基准。
- **分层**：`lib/storage` 不依赖 `lib/modules`。`manual_cycle_correction` 必须由调用方传 `prepare(state, payload, now) -> newState`（12/13 各自 import `applyManualCorrection`）；缺省抛 `INVALID_REQUEST`（`details.reason='prepare_required'`）。04 只强制 `state_version = 旧值 + 1`、`updated_at = now` 并校验结果，不解释 `cycle` 语义。
- **`reset_state` 必须沿用原种子**：先读 `currentState.random.master_seed_hex`，再 `createDefaultState({..., master_seed_hex: prevSeed})`，然后 `state_version = current.version + 1`、`created_at` 保留；`meta.master_seed_id` 不变。只有 `reset_seed` 才重派生（`meta.master_seed_id` 同步更新）。不传原种子会让 02 重新生成种子，与 `meta.master_seed_id` 不一致——这是实现错误，S39 覆盖。
- **两者都会把 `random.streams` 计数器归零**（`createDefaultState` / `RandomProvider.toPersisted()`）：`reset_state` 保留种子但随机序列从头重放，`reset_seed` 换种子并归零。若需要"重置后随机序列继续"，要另设 operation，不在 v1 范围。
- `manual_cycle_correction` 的 `payload = {anchor_at, cycle_length_days?}`；`anchor_at` 必填且为 UTC 毫秒 `Z`，`cycle_length_days ∈ [20,45]`；其余 operation 的 `payload` 必须缺省或为 `{}`。
- **迁移残留与逃生舱**：`meta.state_backup` 非空时，`reset_state` **允许执行并清除** `state_backup` 与 `migration_failed_at`（状态已整体重建，保留备份会在下一次 `loadState` 覆盖刚重置的状态）；`reset_seed` / `manual_cycle_correction` 仍拒绝，返回 `{ok:false, code:'STORAGE_FAILED', details:{reason:'migration_backup_pending'}}`，避免种子与备份分叉。`reset_state` 是迁移失败后唯一的恢复路径，守卫不得把它一起锁死（v1.7.12，P1 修复；S39 第五段覆盖）。
- 无论成败都追加 `evlog` 的 `admin_command` 记录（字段见上）；审计写入失败则拒绝执行（12 §6）。
- 失败写 `meta.recovery_required` 后返回 `code='STORAGE_FAILED'` + `details.recovery_required=true`，**不自动重试**。

## 10. 禁止事项

1. 禁止模块直接依赖 `ctx.storage`、`node:fs` 或 SQLite，必须经由 `StateRepository`。
2. 禁止把 `state`、`evlog`、`idem` 合并成一个大键（突破单键体积与淘汰粒度）。
3. 禁止在写状态成功、事件写失败时保留已推进的状态。
4. 禁止用“先删后写”实现更新，必须单键覆盖或临时文件 + `rename`。
5. 禁止把聊天正文、原始 wxid、令牌写入任何键；`master_seed_hex` **只允许**出现在 `state` 键内（迁移窗口内的 `meta.state_backup` 为唯一例外，见 00 §10.2.1），不得复制到 `evlog`/`idem`/`meta.rollback_state`/快照或日志。
6. 禁止把 `expectedVersion` 校验放到写之后。
7. 禁止修改 `00`；需要新键或新字段时走契约变更流程。
